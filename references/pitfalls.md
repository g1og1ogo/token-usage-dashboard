# 实测坑位与硬约束

每一条都来自本机真实数据上的调试，不是理论推演。改脚本前先读完。

---

## 1. `<user_query>` 陷阱（最致命）

**现象**：Top 会话表里「首条用户意图」几乎全是 `OS Version: win32 / IDE Theme: light`，或者干脆全空。

**原因**：本机会话日志（`.jsonl`）把整段 system prompt + 上下文注入挂在 `role: user` 的消息里，
用户**真正说的话**藏在尾部 `<user_query>...</user_query>` 之中。典型结构：

```
<system-reminder data-role="user-context">      <- 开头，动辄 1 万字符
<user_info>OS Version: win32 ...</user_info>
<working_memory_content>...</working_memory_content>
</system-reminder>
<user_query>这里才是用户真正说的话</user_query>   <- 结尾，通常几十到几百字符
```

两件事同时出错就会全军覆没：

- 直接取 `content[0].text` → 拿到的是注入块
- 用「标签名含 `_` 或 `-` 的成对 XML 标签 = 注入」这条通用规则去剥 →
  `<user_query>` **也含下划线**，会连同用户原话一起删掉

**正解**：先用 `<user_query>` 正则把真身摘出来，再剥残留；没有该标签时，才回退到整块清洗 + 启发式过滤。

## 2. 文本截断预算不能用 `--text-limit`

`--text-limit`（默认 4000）是给**归因**用的，只够看消息开头。
拿它去取用户意图，注入块会把预算吃光，用户正文整个落在窗口外 → 59 个会话只剩 1 条有内容。

意图提取必须用独立的大预算（脚本内写死 200,000 字符）。实测教训：**不要复用归因的截断长度**。

同理，**用户意图必须按 content 块的粒度逐个筛选**，不能把整条消息拼成一个字符串再判——
拼完之后注入特征会污染整串，导致所有候选都被误判为系统文本。

---

## 3. usage 字段名没有统一标准

同一台机器上出现过四种命名，脚本必须全都覆盖，否则会静默少统计（不报错，只会让数字变小）：

| 语义 | 可能出现的键 |
|---|---|
| 容器 | `providerData.usage` / `providerData.rawUsage` / `providerData.tokenUsage` / 顶层 `usage` |
| 输入 | `inputTokens` / `input_tokens` / `promptTokens` / `prompt_tokens` |
| 输出 | `outputTokens` / `output_tokens` / `completionTokens` / `completion_tokens` |
| 缓存 | `cachedTokens` / `cacheReadInputTokens` / 藏在 `inputTokensDetails[0].cached_tokens` |
| 思考 | `reasoningTokens` / 藏在 `outputTokensDetails[0].reasoning_tokens` |

**缓存与思考不在顶层，在 details 数组里**——这是最容易漏掉的一处，漏了会让「缓存率」和「思考占比」恒为 0。

---

## 4. timestamp 有三种形态

秒级整数、毫秒级整数、ISO 字符串都见过。判据：`> 1e11` 视为毫秒，否则 ×1000。
直接当毫秒用会把 1970 年的日期混进日趋势图。

---

## 5. 归因是启发式，不是真相

归因逻辑 = **会话级加权投票**：文件名命中算强信号（1.0）、关键词命中算弱信号（0.3）、
用户原话命中再乘 1.8，最后取票数最高的主线，低于 `--min-score` 记「未归因」。

因此：

- **覆盖率 95% 不代表准确**。它是「有票」的比例，不是「判对」的比例。
- 一个会话跨多条主线时，只能记入消耗最大的那条——跨主线会话的归属必然有偏差。
- 词典里放通用词（「公司」「报告」「方案」）会把无关会话大量吸进来，
  **只放专有名词和文件名词根**。
- 调词典后要重新看覆盖率：覆盖率突然升高往往是被通用词污染了，不是变准了。

## 6. 先天的数据边界

- `output_tokens` 是模型实际生成量，**不含被截断、被用户中断、或失败重试的部分**。
- 同一请求在不同版本里可能被记录多次（重试机制），脚本不去重。
- 本机 log 只反映**这一台机器**；换机或多机并行要分别出看板再合并 JSON。
- 已清理的历史会话不出现在 log 里（本机 `projects` 目录约 68 MB / 63 个文件，
  单次全量扫描在秒级完成，不需要增量）。

## 7. 金额一项坚持不内置单价

脚本**不写死任何模型价格**。不传 `--price-config` 时，「估算成本」列直接不出现，
并在脚注说明原因。

理由：模型单价变动频繁且各家口径不一（是否区分缓存/思考、是否含税、是否有批量折扣），
写死就等于在一份要给人看的看板里放了一个无法核实的数字。

`references/price.example.json` 里的数值**全部是占位样例**，必须替换成用户自己的
合同价或厂商官网现价，并在交付时注明价格来源与生效日期。

---

## 8. 隐私红线：用户原话会进看板

Top 会话表展示的是**真实的 `<user_query>` 原文**。实测本机数据里包含：
自然人姓名、18 位身份证号、企业统一社会信用代码、内部项目路径。

**规则**：

- 自用惯例——默认展示，因为要看的就是自己在做什么
- **任何形式的对外交付（发群、发邮件上会、贴进报告、截图外传）前必须加 `--hide-intent`**
- `--hide-intent` 同时会把 JSON 导出里的 `first_msg` 清空，避免二次泄漏
- 生成的 HTML 是单文件离线文件，**但内容等于本机工作史的摘要**，不能当普通附件随手转发

---

## 9. 输出与运行

- `-o` 不给就用当前目录的 `token-dashboard.html`；路径建议写绝对路径
- 输出目录不存在会自动创建
- Python 仅用标准库，无 `pip install` 依赖
- Windows 控制台可能报 GBK 编码错误，脚本启动时已 `reconfigure(encoding='utf-8', errors='replace')`
- 改完先跑 `--self-test`（不碰真实数据，用内置假数据验证渲染链路），再跑真实数据
- 调试渲染效果时不要拿满是乱码的输出当成功：检查点见 SKILL.md「交付前自查」

---

## 10. 主题

`light` 为默认：用户报告一律走可打印浅色主题，`@media print` 已内建（`break-inside: avoid` 防止卡片被切断页）。
`--theme dark` 仅用于个人大屏盯盘场景，不适合打印。

## 11. 模型名必须先归一，否则同一模型被拆成多行

**现象**：模型分布表里同一模型出现两行，占比被腰斩，看着像有两个不同模型。
实测本机同一模型出现的写法差异：

| 同一模型的不同写法 | 归一后 |
|---|---|
| `Hy4 preview` / `hy4-preview` / `Hy4-preview` | `Hy4-Preview` |
| `Deepseek-V4.1-Flash` / `deepseek-v4.1-flash` | `Deepseek-V4.1-Flash` |
| `GLM-5.3` / `glm-5.3` | `Glm-5.3` |
| `Kimi-K2.7-Code` / `kimi-k2.7-code` | `Kimi-K2.7-Code` |

**原因**：`model` / `requestModelName` 字段直接透传上游，大小写与空格由各 provider 自行决定，无统一标准
（与第 3 条同源：字段名没标准，字段值也没有）。

**正解**：`_canon_model()` —— 折叠空白 → 空格转 `-` → 每段首字母大写。

**必须写成纯函数**：归一结果绝不能依赖调用顺序。踩过的坑——第一版为了保住 `GLM` 这种全大写缩写，
加了「≤4 位全大写段保留原样」的例外，结果 `GLM-5.3` 保留原样、`glm-5.3` 变 `Glm-5.3`，
两种写法仍然归不到同一个 key，表里照样两行。

**另一条错误路线**：在 `_canon_model` 里维护全局别名表、让"含大写的写法"覆盖"全小写的写法"。
看似能显示得更漂亮，实则致命——聚合时用的是函数**当时**返回的字符串，
后续一旦发生别名升级，之前已聚合的旧 key 就与新 key 分裂，问题原样复现。
想要"漂亮的显示名 + 稳定的聚合 key"，必须把聚合 key 与显示名拆成两层，不能挤在一个返回值里。

**代价**：显示为 `Glm-5.3` 而不是 `GLM-5.3`。可接受——同一模型只占一行比大小写好看重要。
改动只影响展示与聚合 key，**不改变任何 token 数字**，故历史快照可继续用于 `--compare-json`。
